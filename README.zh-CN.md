# Semantic Alignment

[English](README.md)

用可直接编辑的 Markdown 保存当前产品与系统设计，并核对两个问题：用户要求是否真正实现，Agent 补足了哪些细节、额外增加了什么。

## 什么时候触发

任务正在建立、改变或纠正长期产品行为、系统接口、架构约束、运行规则或验收标准时使用；用户明确要求维护语义或进行语义审计时也使用。

按既定设计补实现、恢复已有约定的 bug 修复、内部重构、测试调试、Git 操作、安装、临时分析、实验研究及普通写作，默认不触发。项目有语义文件、代码任务较复杂、存在未指定实现细节，都不足以单独触发。既有设计仍须遵守；读取设计不意味着必须启动审计。工作中出现新的长期设计决策时，只针对受影响含义启用。

## 当前设计怎样记录

小项目可只用 SEMANTICS.md。大项目在入口保存共享含义与主题链接，将正文放在 semantics/ 中，按职责和完整行为链组织。描述性文件名、标题和相邻条件支持常见工具的发现、搜索、分段读取与局部修改，不规定工具操作顺序。

Markdown 是直接维护的权威正文，不再使用逐条语义 ID、JSON 账本、生成视图、关系登记表、专用读取器或长期审计缓存。未实现要求留在所属主题并标明已知缺口。仍相关的未采用方案说明当前选择、潜在改进、暂缓理由与重审条件，不默认授权实施。

## 审计应该展示什么

按主题同时展示要求的实际落地和有意义的实现选择，以当前代码、配置、界面、输出或运行结果为证据。明确默认值、存储与数据流、触发条件、失败处理及限制，区分明确要求、Agent 补足和额外机制。内部实现、合理补足或看似有益都不能成为隐藏理由；无法证明的决策理由与必要性保持未知。

检查适用例外和绕过路径，主路径成功不能证明所有路径满足要求。报告说明实际检查范围，局部检查不宣称全项目对齐。当前可用简洁文字、对照表和有帮助的简图；专门审计网页仍暂缓，需以后单独设计。

发现有意义的问题后，还要判断修复需要哪些信息或决策。先复用既有要求、用户回答和授权，调查产物中可查明的事实；只列真正未定的确认点、具体问题及不同答案对修复的影响。已授权且不依赖答案的修复继续进行，不为每个缺陷增加审批。

## 安装与迁移

将本仓库作为名为 semantic-alignment 的 Codex 兼容 Skill 安装。[SKILL.md](SKILL.md) 是入口，两份关联参考文件按需要补充组织和报告说明。

本版替换旧 JSON 工作流。将最新已接受含义、当前缺口及有效替代方案整理成 Markdown，逐一确认条件、禁止项、例外和验收边界没有丢失。停止旧生成器覆盖新记录。旧版仍可通过 Git 历史恢复，日常工作无须加载。
