# 触发与任务范围

## 目的

识别需要语义检查的任务，并维护检查所需的用户语义依据，保持日常工作轻量。

## 限制

普通代码审查和独立画图请求不属于本 Skill；只出现“检查”一词、代码复杂、已有语义文件或存在未指定细节，都不足以触发语义检查。

## 用户约定

### 长期语义维护

**最终期望：** 持续保存用户的有效意图，作为语义检查的基准。

**当前阶段约定：** 为检查维护依据：建立、改变或纠正长期行为、接口、架构约束、运行规则或完成要求时更新记录；用户明确要求维护或澄清语义时也启用。改动小也应保存已接受的长期变化，但只处理受影响含义；维护记录不自动开展完整检查。

按既定设计补实现、恢复已有约定的 bug 修复、内部重构、测试调试、查找仓库、提交、安装、临时实验和普通写作默认不触发。未触发时仍可按需读取并遵守既有语义；读取不等于启动维护或检查。

**本阶段完成条件：** 未单独约定；按当前阶段约定核对。

**关联约定：** 将已接受的长期变更交给[当前含义更新](records.md#当前含义更新)保存。

**关联文件：** [SKILL.md](../../../SKILL.md)：任务入口、语义检查边界和记录格式说明。

### 语义检查入口

**最终期望：** 用户能要求检查实现是否符合自己的语义。

**当前阶段约定：** 明确提出语义检查，或上下文在问“有没有自作主张”“是不是按我的要求做的”等意图对照问题时，开展语义检查及结果交付，不要求出现“语义”关键词。代码检查服务于查明实际行为，逻辑缺陷作为解释语义偏差的证据；不承担普通代码审查的流程和交付。没有现成语义记录时也可根据当前用户要求和可用来源检查，缺少依据如实说明。修改既有检查图属于报告交付环节，不另开独立可视化流程，也不因改图而声称重新验收产品。

**本阶段完成条件：** 未单独约定；按当前阶段约定核对。

**关联约定：** 按本次范围启动[要求与产物双向对照](audit.md#要求与产物双向对照)；将发现交给[结果呈现与交付](audit.md#结果呈现与交付)呈现。

**关联文件：** [SKILL.md](../../../SKILL.md)：任务入口、语义检查边界和记录格式说明；[audit-presentation.md](../../../references/audit-presentation.md)：双向核查、选择披露、修复信息和交付规则。
